# 백업·복원·가동 감시·되돌리기 리허설

## 배경

배포했다는 것만으로는 장애가 났을 때 복구할 수 있는지 알 수 없다. 런북의 운영 절차를 실제 서버에서 한 번씩 실행해서 확인하고, 다음 날 일별 재계산이 정상인지도 본다.

- **필요한 결정:** 사용자 행동 U7(감시 서비스 가입)과 Q6(백업 보관 위치)
- **로그 확인:** 백엔드가 멈췄을 때 Caddy 프록시 오류 로그에 요청 URI(좌표 쿼리 포함)가 남는지는 확인하지 못했다(확실하지 않음). 이 이슈에서 확인한다.
- **실행자:** 3-1과 같이 서버에 접속할 수 있는 사람이 한다.

## 범위

- **포함:**
  - cron 백업 확인, 다음 날 일별 재계산 확인
  - 복원 리허설, 서버 밖 사본 1회
  - 감시 등록과 알림 확인
  - Caddy 오류 로그의 좌표 확인
  - 되돌리기 리허설
  - 런북 수정
- **제외:**
  - 이 이슈 이후의 정기 운영(런북대로 한다)
  - 헬스 체크 기준값(60분·3일) 조정. 1주 운영 뒤 따로 판단한다.

## 할 일

1. 런북 "백업·복원", "가동 감시", "업데이트", "되돌리기" 절을 순서대로 실행한다.
2. 다르게 동작한 곳은 같은 PR에서 런북을 고친다. 걸린 시간도 런북에 적는다.

## 인수 조건

### 서버에서 확인

- [ ] cron을 등록한 다음 날 `BACKUP_DIR`에 백업이 1개 생기고, `tar -tzf`로 보면 `out/country_meta.csv`가 있다. 백업 크기를 런북에 적는다. [명령]
- [ ] 다음 날 일별 재계산이 끝난 뒤 두 가지를 확인한다. [명령]
  - `/api/health`의 `index_date`가 어제(UTC)나 그 전날이다.
  - `find /srv/war-risk-index/data /srv/war-risk-index/out -name '*.part'` 결과가 0건이다.
- [ ] 복원 리허설: 최신 백업으로 런북의 복원 절차를 끝까지 실행한다. [명령]
  - 끝난 뒤 `/api/health`, `/api/pairs`, `/api/countries`가 200이다.
  - 걸린 시간을 런북에 적는다.
  - 보관본을 지운다. 지우기 전에 대상 목록을 보여 준다.
- [ ] Q6에서 정한 방식으로 백업 1개를 서버 밖에 복사한다. 복사본 크기가 원본과 같다. [명령]
- [ ] 외부 감시에 `https://<도메인>/api/health`와 `https://<도메인>/` 두 주소가 5분 간격으로 등록돼 있다. [수동]
- [ ] `sudo systemctl stop war-risk-api` 뒤 15분 안에 장애 알림 메일을 받는다. `start` 뒤 15분 안에 복구 알림을 받는다. [수동]
- [ ] 백엔드가 멈춰 있는 동안 Caddy 로그에 좌표가 남지 않는지 확인한다. [명령]
  - `curl -s "https://<도메인>/api/shelters?lat=37.57&lon=126.98"`을 보낸다. 502가 예상된다.
  - 그 뒤 `journalctl -u caddy --since "10 min ago" | grep -c "lat="`이 0이다.
  - 0이 아니면 `deploy/Caddyfile`에 Caddy 오류 로그에서 요청 URI를 빼는 설정을 추가하고 다시 확인한다.
- [ ] 되돌리기 리허설: `/api/health`가 들어 있는 이전 커밋 하나로 되돌린다. [명령]
  - 설치·빌드·재시작한 뒤 `/`와 `/api/health`가 200이다.
  - 다시 최신 커밋으로 돌아와 같은 확인을 한다.
  - 두 방향 모두 걸린 시간을 런북에 적는다.
- [ ] 리허설하면서 고친 런북 내용이 커밋돼 있다. 고칠 곳이 없었으면 PR에 "차이 없음"이라고 적는다. [수동]
