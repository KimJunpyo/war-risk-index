# 데이터 신선도 헬스 체크 `/api/health`

인용 줄 번호는 `466b1a9`(M9 시작 전 main) 기준이다.

## 배경

갱신 스레드가 멈추거나 외부 데이터가 끊겨도 API는 마지막 파일로 200을 준다.
- `/api/live`가 최신 15분 슬롯(`as_of`)을 알려 주지만, 일반 가동 감시 서비스는 그 시각이 지금보다 얼마나 오래됐는지 계산하지 못한다.
- 무료 등급은 대부분 HTTP 상태 코드만 본다. 키워드 감시는 유료일 수 있다(확실하지 않음).
- 따라서 서버가 직접 "오래됨"을 503으로 알려야 밖에서 감지할 수 있다.

**판단: 필요하다.** 혼자 운영하면 로그를 늘 보지 않는다. 그래서 이것이 핵심 데이터 두 가지의 멈춤을 알 수 있는 유일한 수단이다. 범위는 최소로 잡아 핵심 데이터 두 가지만 본다.

## 범위

- **포함:** `GET /api/health`(`HEAD` 포함), 기준 상수, 테스트
- **제외:**
  - 여행경보·대피소·재외공관의 신선도. 하루 1회 갱신하고, 실패해도 이전 파일로 계속 동작하며 다음 주기에 다시 시도한다.
  - UCDP 집계 신선도(실패는 로그에만 남음, 1-2). 월 1회 `.asof`로 따로 확인한다(2-3).
  - 화면 표시(`plan.md` 12절 제안)
  - 알림 발송. 외부 감시 서비스가 맡는다(2-3, 3-2).

## 스펙

| 항목 | 내용 |
|---|---|
| 경로 | `GET /api/health`. `HEAD`도 같은 상태 코드를 준다. 감시 서비스 가운데 HEAD로 확인하는 곳이 있고, FastAPI의 GET 경로는 HEAD에 405를 준다(FastAPI 0.162에서 확인). 그래서 같은 함수에 `@app.get`과 `@app.head`를 함께 붙였다. `@app.api_route(methods=["GET", "HEAD"])`로 묶으면 두 메서드에 같은 operationId가 생겨 "Duplicate Operation ID" 경고가 난다. |
| 용도 | 외부 가동 감시 전용이다. Caddy 업스트림 헬스 체크에는 쓰지 않는다(2-1). 데이터가 오래되면 일부러 503을 주므로, 쓰면 데이터만 멈춰도 정상 파일로 응답하던 `/api/pairs`·`/api/countries`까지 막힌다(M9 리뷰). |
| 실시간 기준 | `data/live/country_15min.csv`의 최신 슬롯(`/api/live`의 `as_of`와 같은 값, UTC)이 현재 UTC로부터 `LIVE_STALE_MINUTES = 60`분 이내 |
| 일별 지수 기준 | `out/country_meta.csv`의 `date` 최댓값이 오늘(UTC)로부터 `INDEX_STALE_DAYS = 3`일 이내 |
| 200 | 두 기준을 모두 만족한다. |
| 503 | 하나라도 넘었거나 파일·값이 없다. 500이 아니다. |
| 본문(200·503 같음) | `ok`(bool), `live_as_of`(문자열\|null), `live_age_minutes`(정수\|null), `index_date`(문자열\|null), `index_age_days`(정수\|null). 이 5개만 넣고 경로·오류 메시지는 넣지 않는다. |
| 나이 계산 | `live_age_minutes`: 현재 UTC − 최신 슬롯 시각을 분 단위로 내림한 정수다(59분 30초 → 59). 미래 슬롯이면 음수이고 정상이다(−11분 15초 → −12). 하한 검사는 두지 않는다.<br>`index_age_days`: 오늘(UTC) 날짜 − `index_date`의 달력 날짜 차다. 하루 중 시각과 상관없다(23:59:59에도 3일 전은 3).<br>판정도 이 정수로 하고 "이내"는 포함이다. 60분 00초·60분 59초는 60이라 200, 61분 00초부터 503이다. 3일은 200, 4일부터 503이다. |
| 읽기 | 기존 `_csv` 캐시를 쓴다. mtime이 바뀌지 않으면 다시 읽지 않는다. |
| `LIVE_UPDATES=0` | 같은 기준으로 판단한다. 로컬에서 갱신을 끄면 데이터가 멈추므로 기준을 넘은 뒤 503이 정상이다. |

**기준값 근거(M9 실측으로 바꿈)**
- **60분:** GDELT 2.0 슬롯 key는 파일 발행 시각(Last-Modified)보다 약 10~11분 늦다(M9 리뷰 실측 599~694초, 2026-11-12에 다시 본 값 646초). 갱신은 15분 간격이다. 그래서 `live_age_minutes`의 정상 범위는 약 −11~+20분이고(내림이라 −12도 나올 수 있다), 갱신 직후에는 음수가 정상이다. 60분 기준에는 약 40분 여유가 있다. 기획 때 예상(정상 최대 약 30~45분)보다 작다.
- **3일:** D일 GDELT 1.0 파일은 D+1일 07:00 UTC 무렵 올라온다(M9 리뷰에서 최근 6일 확인, 2026-11-12에 2일 다시 확인). 그래서 `index_age_days` 정상값은 1~2이고, 3일 기준에서 거짓 알림은 없다.
- 두 값 모두 3-2 이후 1주 운영 기록을 보고 조정할 수 있다.
