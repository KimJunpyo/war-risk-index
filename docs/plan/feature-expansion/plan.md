# 전쟁 가능성 지수 기능 확장 기획안 (비상 대비·오프라인·국가 상세·테마)

작성일: 2026-11-17 · 상태: 초안 · 열린 질문 Q1~Q14 미결(결정 전에는 추천안 기준으로 진행) · 이전 기획: `docs/plan/deploy-prep/`(GitHub M9~M11), M12(Workers 이전, 이슈 #49~#55) · 코드 기준: `5acdd59`(`main`, 2026-11-17)

## 1. 목표

사용자가 고른 네 기능을 지금의 0원 운영 구조 안에서 더한다. 운영 구조는 웹 Vercel Hobby, API Cloudflare Worker(무료), 저장 R2, 데이터 GitHub Actions 15분 배치다.

1. **민방위 경보별 행동요령과 비상 가방:**
   - 민방공 경보 종류마다 해야 할 일을 정리한다.
   - 비상 가방은 들고 나가는 3일치 가방과 집에 두는 7일 이상 비축으로 나눈다.
   - 가구원 수를 넣으면 물·식량 양을 계산한다.
   - 이 셋을 새 페이지 `/emergency` 하나에 둔다(주소는 제안).
2. **오프라인 비상 정보(PWA):** 직접 만든 서비스 워커로 `/emergency`를 기기에 저장해 인터넷 없이 연다. 저장 대상은 행동요령, 체크리스트, 계산기, 재외공관 연락처다.
3. **국가별 상세 페이지:**
   - 나라마다 `/countries/{코드}` 한 주소에서 점수 추이, 뉴스, 여행경보, 공관 연락처를 보여 준다.
   - 목적은 검색 노출과 링크 공유다.
4. **라이트/다크 테마:**
   - 색을 의미별 토큰으로 바꾸고 라이트 테마를 더한다.
   - 기본은 시스템 설정을 따르고, 수동 전환을 둔다.

## 2. 대상 사용자

- **일반인:** 기존과 같다. 휴대폰(360px)부터 데스크톱(1440px)까지 쓴다.
- **국내 거주자:** 비상 상황에 대비한다. 경보의 뜻, 해야 할 일, 준비물과 양을 빨리 찾는다. 통신이 끊긴 상황(오프라인)도 가정한다.
- **해외 체류자·여행 예정자:** 검색이나 공유받은 링크로 나라 페이지에 들어와 여행경보와 공관 연락처를 본다.
- **밝은 화면 사용자:** 시스템 라이트 모드를 쓰거나 낮에 밖에서 본다.

## 3. 원칙

1. **불완전한 것은 보여 주지 않는다.**
   - 데이터나 근거가 없는 영역은 숨긴다.
   - 공식 근거를 확인하지 못한 수치·기간은 넣지 않는다. 필요하면 "확실하지 않음"으로 남기고 열린 질문에 올린다.
2. **0원으로 운영한다.**
   - 유료 API와 유료 플랜은 쓰지 않는다.
   - 새 npm·Python 패키지는 0개가 목표다. 필요하면 이슈에서 먼저 알리고 이유를 적는다.
   - 서비스 워커도 라이브러리(Serwist 등) 없이 직접 만든다.
3. **문구는 자체 작성하고, 출처는 링크와 확인일로만 단다.** 공식 문장을 옮기지 않는다. 기존 체크리스트와 같은 방식이다.
4. **위치 개인정보 원칙을 지킨다.**
   - 페이지를 열 때 위치를 묻지 않는다.
   - 좌표는 소수 2자리로 반올림한다.
   - 위치와 검색어를 브라우저 저장소에 남기지 않는다.
   - 오프라인 저장과 충돌하는 부분은 Q4에서 정한다.
5. **정적 렌더링을 우선한다.**
   - 페이지는 정적으로 생성하고, 필요하면 주기적으로 다시 생성한다.
   - 요청마다 서버에서 렌더링하는 방식(쿠키·헤더 읽기)은 쓰지 않는다.
   - Worker는 R2 JSON을 그대로 내주는 얇은 구조를 유지한다(요청당 CPU 10ms).
6. **`main` 머지는 곧 운영 배포다.**
   - Vercel이 `main`을 자동으로 배포한다.
   - `worker/` 변경은 `worker.yml`이 배포한다.
   - `publish.py`·`batch.py` 변경은 다음 15분 배치부터 R2에 반영된다.
   - 그래서 PR 하나가 혼자 배포돼도 깨진 화면이 나가면 안 된다. 새 응답이 아직 없으면 그 영역을 숨긴다.
7. **기존 기준을 새 화면에도 적용한다.**
   - 반응형 기준: 360/768/1080/1440px, `md`/`lg`/`xl`
   - 오버레이 스크롤바
   - 명도 대비 AA 계약
   - `docs/design/`가 없으므로 7절이 시안을 대신한다.

### 확인한 사실 중 기획에 영향 주는 것

**사실 1. 공식 민방공 경보는 핵경보를 포함해 5종이다.**
- **경보 종류(국민안전24 '민방위 경보' 쪽, 행정안전부, 2026-11-17 확인):**

  | 경보 | 발령 상황 | 알리는 방법 |
  |---|---|---|
  | 경계경보 | 공격이 예상될 때 | 음성방송·문자. 사이렌 없음 |
  | 공습경보 | 공격이 임박했거나 진행 중일 때 | 사이렌 + 음성방송 |
  | 화생방경보 | 화생방 작용제가 살포·탐지됐을 때 | 음성방송 |
  | 핵경보 | 핵공격이 임박했거나 진행 중일 때 | 사이렌 + 음성방송 |
  | 경보해제 | 추가 공격이 예상되지 않을 때 | 음성방송 |

  - 사이렌은 1분 동안 5초 오르고 3초 내린다.
- **행동요령 출처:**
  - 국민안전24 '민방공경보' 행동요령: 경계·공습(주간·야간), 화생방, 핵
  - 국민안전24 '비상대비' 행동요령: 경보해제 때 할 일(부상자 구조 돕기, 추가 공습 대비, 정부 방송 계속 듣기)
- **요청 목록과의 차이:** 요청 목록(경계·공습·화생방·해제)에는 핵경보가 없다 → Q1
- **출처 간 차이:**
  - 일부 지자체와 옛 포털 쪽은 공습경보 사이렌을 "3분", 경계경보를 "1분 평탄음"으로 적는다.
  - 국민안전24 '민방위 경보' 쪽을 1순위로 쓰고, 차이는 1-2 PR에 기록한다.
- **범위 밖:** 재난경보(자연재난 사이렌 12초)

**사실 2. 비상 가방·비축의 공식 근거 (2026-11-17 확인)**

| 출처 | 기간 | 물 | 확인 방법 |
|---|---|---|---|
| 국민안전24 '비상대비' 행동요령(행정안전부) | 생존배낭 "2~3일분", 한 사람에 하나<br>핵 폭발 이후 비상대비물자 "2주" | 리터 수치 없음 | 원문 열람 |
| 국민안전24·옛 국민재난안전포털 '비상대비용품' | 가정에 최소 3일 버틸 생필품<br>옛 쪽에는 식량·식수 "30일분" 문구가 있다 | 없음 | 검색 결과 요약만 봤다. 현행 쪽에서는 30일 문구를 확인하지 못했다 |
| 일본 농림수산성·총리관저 | 최소 3일, 가능하면 1주 | 1인 1일 약 3L(마실 물+조리), 1주 21L | 검색 결과 요약. 원문은 1-3에서 확인 |
| 스웨덴 MCF(옛 MSB) | "가정 대비: 1주"(메뉴 이름) | 성인 1일 3~5L | 원문 열람(검토일 2026-10-01) |
| 독일 BBK | 가능하면 10일. 최소 3일도 도움 | 1.5L + 조리용 0.5L | 원문 열람 |
| 미국 Ready.gov | 며칠(several days) | 1인 1일 1갤런(약 3.8L, 마실 물·위생) | 원문 열람(2021-02-22 갱신) |

- **결론:**
  - 3일 가방은 국내 공식 근거가 있다.
  - 7일 비축은 일본·스웨덴(1주), 독일(10일), 국내(핵 이후 2주)에 공식 근거가 있다.
  - 30일은 현행 공식 쪽에서 확인하지 못했다. 물만 1인 약 90L(3L × 30일)라 가방이 될 수 없으므로 넣지 않는다.
- **국내 물 수치:** 국내 공식 쪽에서는 물의 리터 수치를 확인하지 못했다.
  - 기존 체크리스트의 "1인 1일 약 3L"는 일본 농림수산성 값과 같고, 스웨덴 범위(3~5L)의 하한과 같다 → Q3

**사실 3. 무료 한도 (2026-11-17 확인)**
- **Vercel Hobby:**
  - 빌드는 최대 45분이다(2 vCPU, 8GB).
  - 월 포함량:

    | 항목 | 포함량 |
    |---|---|
    | 함수 호출 | 100만 회 |
    | Active CPU | 4시간 |
    | CDN 요청 | 100만 건 |
    | ISR 읽기 | 100만 단위(8KB) |
    | ISR 쓰기 | 20만 단위(8KB) |

  - ISR 값은 가격 쪽 기준이다. Hobby 문서 표에는 ISR 항목이 없어 확실하지 않다.
  - 다시 생성한 결과가 이전과 같으면 ISR 쓰기가 생기지 않는다.
  - 한도를 넘으면 30일 동안 그 기능을 쓰지 못한다.
- **Cloudflare Workers 무료:** 하루 10만 요청, 요청당 CPU 10ms(사용자 메모)
- 계산은 8절에 있다.

**사실 4. Next 16(Cache Components)의 제약** (`frontend/node_modules/next/dist/docs/` 확인)
- **`generateStaticParams`:**
  - 1개 이상을 돌려줘야 한다. 빈 배열이면 빌드 오류다.
  - 목록 밖 값은 첫 방문 때 만들어 저장한다("ISR with Cache Components" 가이드).
- **재생성 주기:**
  - `'use cache'`와 `cacheLife`로 정한다. 렌더 결과에 내용이 같으면 쓰기가 생기지 않는다.
  - 서버리스에서는 캐시 함수의 결과가 요청 사이에 남지 않는다. 그래서 여러 페이지가 함께 쓰는 함수도 페이지를 다시 생성할 때마다 다시 실행된다(`use-cache.md`).
  - `expire`가 5분 미만이면 사전 렌더에서 빠진다.
- **테마와 쿠키:**
  - 루트 레이아웃에서 `cookies()`를 읽으면 앱 전체가 정적 사전 렌더에서 빠진다.
  - 문서는 테마를 `<head>` 인라인 스크립트, `localStorage`, `data-theme` 속성으로 처리하라고 안내한다(`preventing-flash-before-hydration.md`).
  - 개발 모드에서는 Strict Mode가 `<html>` 속성을 지우므로 `useLayoutEffect`로 다시 붙인다.
- **OG 이미지:** `ImageResponse`는 글꼴을 포함한 번들이 500KB로 제한되고, ttf·otf·woff만 받는다. 지금 OG 이미지가 영문인 이유다.
- **PWA 가이드:**
  - `/sw.js`에 `Content-Type`과 `Cache-Control: no-cache, no-store, must-revalidate` 헤더를 권한다.
  - `experimental.useOffline`은 소프트 이동만 다룬다. 전체 오프라인 로드에는 서비스 워커가 필요하다고 적혀 있다.

- **Playwright:** 서비스 워커 기능(등록 확인, 요청 가로채기)은 Chromium 계열만 지원한다. 지금 e2e는 Firefox·WebKit만 돈다 → Q6

**사실 7. 기존 테스트가 새 작업에 거는 제약**
- **`test_m8_contrast.py`:** 어두운 회색 글자·채움·밑줄을 금지한다. 라이트 테마에서는 어두운 글자가 필요하므로 계약을 바꿔야 한다(4-3, 명세 변경).

  - 영숫자와 `%XX` 인코딩이 32자 이상 이어지면 실패한다. `docs/`도 검사한다.
  - 그래서 서비스 워커 캐시 이름이나 버전에 해시를 넣지 않는다.
- **e2e와 서비스 워커:**

  - 개발 모드에서는 서비스 워커를 등록하지 않는다(2-3).
  - 그래서 오프라인 검사는 프로덕션 빌드에서 한다.

## 5. 순서와 근거

사용자가 추천받은 순서(경보·가방 → 오프라인 → 국가 상세 → 테마)를 따른다. 다만 테마의 첫 단계인 의미 색 토큰 정의만 맨 앞(1-1)으로 당긴다(Q13).

- **토큰을 당기는 이유:**
  - 새 화면 `/emergency`·`/countries/[code]`를 팔레트 클래스로 만들면, M4에서 같은 파일을 다시 고쳐야 한다.
  - 토큰 정의는 반나절 크기이고 화면이 바뀌지 않는다.
- **오프라인(M2)이 M1 뒤인 이유:** M1의 `/emergency`를 저장하기 때문이다.
- **국가 상세(M3):**
  - 서버에서 M2의 공관 묶음 응답(2-1)을 다시 쓴다. Worker 요청이 줄어든다.
  - 2-1만 먼저 끝나면 M2와 동시에 진행할 수 있다.
- **테마(M4)가 마지막인 이유:**
  - 기존 컴포넌트 전환과 라이트 값이 대부분이라, 새 화면이 다 들어온 뒤 대비 검사를 한 번에 한다.
  - `HomePage.tsx` 같은 파일을 M1·M3도 고치므로, 충돌을 피하려고 마지막에 둔다.

## 8. 무료 한도 계산 (추정치, 3-2·3-5에서 실측)

가정: 대상 나라 N = 81(로컬 기준, Q7), 재생성 6시간(나라마다 하루 최대 4회, 요청이 있을 때만), 재생성 1회 서버 처리 시간 t(3-2에서 측정).

| 항목 | 계산 | 값 | 한도 대비 |
|---|---|---|---|
| Worker 요청(서버) | 4회 × 81 × 2건(countries·embassies) + `/emergency`·sitemap | 하루 약 700건 | 하루 10만의 1% 미만 |
| Worker 요청(브라우저) | 상세 1회 볼 때 4건 이하(3-3) | 하루 1,000회 보면 4,000건 | 4% |
| ISR 쓰기 | 일별 값이 하루 1번 바뀌므로 81 × 30 × (페이지 출력 ÷ 8KB). 출력 60KB로 가정 | 월 약 2만 단위 | 20만의 10%(재생성마다 바뀌는 최악의 경우 39%) |
| Active CPU | 81 × 4 × 30 × t. t = 0.2초로 가정 | 월 약 0.54시간 | 4시간의 14% |
| 함수 호출 | 81 × 4 × 30 + OG·sitemap | 월 약 1만 회 | 100만의 1% |
| 빌드 | 나라 페이지 81개 + OG 이미지 81개 추가 | 측정(3-2·3-5) | 45분 한도 |

- **판단 규칙:**
  - 3-2에서 잰 t로 계산한 월 최악 Active CPU가 1시간(포함량의 25%)을 넘으면 재생성 주기를 12시간으로 늘린다.
  - 서버 렌더 결과에 현재 시각이 들어가면 재생성마다 ISR 쓰기가 생긴다. 그래서 상대 시각("…분 전")은 브라우저 영역에만 둔다.
- **서비스 워커:** 새 방문자마다 `/emergency` HTML과 정적 파일을 한 번 받는다(CDN). 크기는 2-3에서 측정한다.

- **충돌:**

  - 화면 문구는 "위치는 대피소 검색에만 쓰고 저장하지 않습니다"다.
  - 위치 조회 결과(5km 안 대피소와 거리)를 저장하면, 좌표가 없어도 사는 곳을 약 1km 범위로 짐작할 수 있다.
- **선택지:**

  | 선택지 | 저장하는 것 | 장점 | 단점 |
  |---|---|---|---|
  | A | 아무것도 저장하지 않는다. 오프라인 화면에는 "대피소 찾기는 인터넷이 필요합니다"와 공식 앱(안전디딤돌) 안내만 둔다 | 원칙 그대로 | 오프라인에서 쓸모가 낮다 |
  | **B(추천)** | 지역(시·도, 시·군·구)으로 찾은 결과만 저장한다. 사용자가 "이 기기에 저장"을 누를 때만, 한 지역을 Cache Storage에 둔다. 위치 결과에는 저장 버튼이 없다 | 오프라인에서 결과 검색이 된다(창원시 527곳, 약 149KB) | 저장 버튼·지우기 버튼이 필요하다 |
  | C | 위치 결과(거리 포함)도 누를 때만 저장한다 | 가장 쓸모 있다 | 위치에서 나온 정보가 기기에 남는다. 화면 문구와 인수 조건을 "누를 때만 저장"으로 바꿔야 한다 |

- **B를 추천하는 이유:**
  - 지역은 사용자가 고른 값이지 GPS 위치가 아니다.
  - 저장은 명시적인 동작이 있을 때만 일어난다.
  - 기존 문구("위치는 … 저장하지 않습니다")가 그대로 참이다.
- **B로 정하면 바뀌는 인수 조건:** "위치와 검색어는 저장하지 않는다. 지역 결과는 사용자가 저장을 누를 때만 이 기기(Cache Storage)에 남는다."
- 저장 화면에는 저장 시각과 "지우기"를 둔다.

1. **위치 조회 응답 `no-store`(Q14):** Worker의 위치 조회 캐시 헤더를 `no-store`로 바꾸고 테스트를 고친다.
2. **`/countries` 목록 페이지:** 대상 나라를 가나다순으로 링크한다(내부 링크, 검색 노출).
3. **국가 쌍 상세 페이지:** 예: `/pairs/KOR-PRK`
4. **한글 OG 이미지:** 나라 이름 글자만 부분 집합 글꼴로 넣는다.
5. **재난경보 행동요령:** 호우·지진 등. 같은 `/emergency`에 영역을 더한다.
